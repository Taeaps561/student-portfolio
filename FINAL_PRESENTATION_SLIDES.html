🌐 การรับส่งข้อมูลระหว่างส่วนต่าง ๆ
  • Client ↔ Edge: สื่อสารผ่าน HTTPS (TLS 1.3) ฉีด HTTP Security Headers 7 รายการสกัดกั้น Clickjacking และ XSS
  • Edge ↔ Application: NextAuth ตรวจสอบ HttpOnly Cookie สกัดการขโมย Session ผ่าน JavaScript
  • Application ↔ Database: ส่งคำขอผ่าน Prisma ORM โดยใช้ Parameterized Queries 100% ป้องกัน SQL Injection
  • External GitHub API: ส่ง Request ด้วย Regex Whitelist ตรวจสอบ username ป้องกันการโจมตีแบบ SSRF

⏱️ Secret Management
🔐 การจัดการ Environment Variables & Secrets
  • Local Isolation: ใช้ไฟล์ .env เก็บค่าเฉพาะเครื่องตนเอง และจัดทำ .env.example โดยไม่มี Secret จริง
  • Git Protection: กำหนด .gitignore ละเว้น .env, *.db, node_modules/ 100%
  • Vercel Encrypted Secrets: บน Cloud จัดเก็บ DATABASE_URL, NEXTAUTH_SECRET, GITHUB_SECRET บน Vercel Project Settings แบบเข้ารหัส
  • Semgrep Secret Scanning: ติดตั้ง Ruleset p/secrets ใน CI Pipeline สแกนจับรหัสผ่านก่อนเข้าสู่ Repo
⚡ เหตุผลในการเลือกใช้เทคโนโลยีแต่ละส่วน
  • Next.js 16 (App Router): รวมหน้าบ้านและหลังบ้าน มี Server Components ป้องกันข้อมูลรั่วไหลสู่ Client
  • Prisma ORM: รองรับ Type-safe และใช้ Parameterized Queries เป็นค่าเริ่มต้น กำจัดปัญหา SQLi
  • NextAuth.js: มาตรฐานการจัดการ Session ด้วย Secure Cookie (HttpOnly, SameSite) ที่แข็งแกร่ง
  • Node.js Native Crypto: สร้าง SHA-256 Hash เพื่อรับรองความถูกต้องของข้อมูลใบประกาศนียบัตร

🛡️ หลักการ DBMS Security ที่นำมาประยุกต์ใช้

🛡️ การป้องกันข้อมูลสำคัญ

  • Data Masking (PDPA): ซ่อน GPA และแปลงเบอร์เป็น 081-XXX-XXXX

🌿 Git Workflow & Branching Strategy
  • Branch Protection: สาขา main ป้องกันการ Push โดยตรง ต้องผ่าน Pull Request (PR)
  • Feature Branches: สมาชิกสร้าง Branch ย่อย เช่น feat/security-remediations, fix/headers

1.5 กระบวนการ DevSecOps (Automated CI/CD Pipeline)
การทำงานของ GitHub Actions & Security Quality Gates
⏱️ sast-security.yml
⚙️ 6 ขั้นตอนใน Security Pipeline
  • 1. Dependency Installation: รัน npm ci ตาม package-lock.json
  • 2. Prisma Validation: ตรวจสอบความสมบูรณ์ของ Schema
  • 3. ESLint Static Scan: ตรวจสอบโค้ดไวยากรณ์และ Security Lints
  • 4. npm audit: ตรวจสอบช่องโหว่แพ็กเกจระดับ High/Critical
  • 5. Semgrep SAST: สแกนกฎ security-audit, secrets, owasp-top-ten
  • 6. Build Verification: ทดสอบคอมไพล์ npm run build
🚦 เงื่อนไขการผ่าน / ไม่ผ่าน Pipeline (Quality Gate)
  • ❌ Pipeline FAIL: เกิด Compile Error, Syntax Error, หรือการ Build Production ล้มเหลว → บล็อกการ Merge เข้าสู่ main ทันที
  • ✅ Pipeline PASS: โค้ดผ่านการทดสอบ ไม่พบปัญหาความปลอดภัยระดับบล็อกเกอร์ และ Build สำเร็จ
  • CD Trigger: เมื่อ Merge เข้าสู่ main แล้ว Vercel จะทำการ Deploy ขึ้น Production อัตโนมัติ

1.6 การประเมินความเสี่ยงและช่องโหว่ (Environment Comparison)
เปรียบเทียบผลตรวจ Localhost vs Vercel Deploy & ข้อจำกัด
⏱️ Environment Limitations
💻 สภาพแวดล้อม Localhost
  • ข้อดี: ตรวจสอบได้ลึกถึง Source Code และ Database โดยไม่มี Rate Limit
  • การทดสอบ: รัน Burp Suite Repeater และ OWASP ZAP Full Scan ได้เต็มประสิทธิภาพ
  • ข้อจำกัด: ไม่ได้ทดสอบผ่านโครงข่ายจริง ขาดการจำลอง SSL/TLS Handshake และพฤติกรรมของ Edge CDN
☁️ สภาพแวดล้อม Production (Vercel Deploy)
  • ข้อดี: ตรวจสอบบน HTTPS (TLS 1.3) จริง มี Vercel Edge ป้องกัน DDoS เบื้องต้น
  • ข้อจำกัดด้านการสแกน: ไม่สามารถรัน Active DoS/Fuzzing Scan ได้เพราะจะติด WAF หรือใช้ Serverless Quota จนหมด
  • ข้อจำกัด Filesystem: Vercel มีสภาพแวดล้อมเป็น Ephemeral Serverless ไม่สามารถเขียนไฟล์ลง Local Disk ได้ จึงต้องใช้ External PostgreSQL
